# CLI 运行时架构与生命周期

状态：设计说明，尚未实现。本文确定短命令与持续会话的职责边界；IPC、资源协议和异常恢复的实现细节仍待收敛。

相关设计：[drive](drive.md)、[target](target.md)、[override](override.md)。

## 1. 基本原则

Android CLI 入口为 `aeu`，iOS CLI 入口为 `ieu`。每次执行命令通常创建一个新的操作系统进程，命令完成后进程退出。

一次 CLI 请求的生命周期与一次 App 调试会话的生命周期不同：

- 命令负责提交请求并取得结果。
- 会话负责持续连接目标 App，并承载 SDK 运行时。
- watcher、override 等资源在会话中持续存在，直到被显式清理或其运行时失效。

持续存活不表示永久存活，而是不随某一条 CLI 命令结束而结束。

```bash
aeu connect --app com.example.demo
aeu override method --class com.example.FeatureConfig \
  --method isEnabled --argument-types '[]' --return true
aeu drive click --target R.id.search_button
aeu override remove ov-1
```

这四条命令可以由四个不同的 CLI 进程执行。第二条安装的覆盖必须在第二条命令退出后继续生效，第三条才能验证其效果，第四条才能移除它。因此，连接、回调和清理闭包不能仅由短命 CLI 进程持有。

## 2. 三个执行位置

```text
aeu / ieu CLI 进程
  │ 每次命令创建，完成后退出
  │ 本地 IPC：提交请求、接收结果
  ▼
Host 控制服务
  │ 跨命令存活，持有设备连接与 App 会话
  │ 运行时通信
  ▼
App 内 SDK JS 运行时及资源管理层
    随对应会话存活，持有 watcher、hook、原生对象和清理闭包
```

两种 CLI 入口可以共用 Host 控制服务，以平台、设备和会话身份隔离状态。Android / iOS 的实际能力与底层后端仍分别实现。

### CLI：请求与输出

CLI 负责解析参数、提交请求、等待结果、输出 JSON 并设置退出码。诊断日志写 stderr，结构化结果写 stdout，避免混杂。

CLI 不负责长期持有原生连接、watcher 或清理闭包。需要读取的 JS 文件由 CLI / Host 加载并传送，但覆盖安装函数与原生回调在 App SDK 运行时执行，不在 CLI 的 Node.js 进程中执行。

### Host：会话与控制状态

Host 控制服务负责连接复用、请求路由、会话身份和资源映射，例如：

```text
Android 设备 A
  └─ App 会话 S1
       ├─ 目标进程身份
       ├─ SDK 运行时身份
       ├─ 运行时通信连接
       └─ override ov-1 → 运行时资源 r-7
```

下一条命令到来时，服务继续使用同一会话，不为每条命令重新注入 SDK、初始化运行时或安装已有覆盖。

建议首次需要连接时自动启动本地控制服务，无须用户预先手动启动 daemon。CLI 与服务可以使用 Unix socket 等本地 IPC；具体方式尚未确定。并发启动、服务版本兼容、请求调度和退出策略需在实现设计中补齐。

### App 运行时：实际行为与资源

原生对象、hook 回调和闭包位于 App 运行时。例如 SDK 调用：

```javascript
const remove = await override.method(definition, returnInstead);
```

remove 可能引用原方法实现、原生对象和清理状态，不能作为 JSON 传到 Host 后在另一进程中还原。

建议由 SDK API 之外的运行时管理层保存资源：

```text
r-7 → remove 闭包
r-8 → log watcher
```

SDK 继续返回其原有闭包或 watcher，不必为 CLI 改为返回 ID。管理层登记资源身份；Host 再维护用户可见 ID 与运行时资源之间的映射。运行时资源 ID 的具体协议尚待确定。

method 的 filter、动态返回和 Android code 同步回调在命中线程按 SDK 契约执行，不往返 Host 请求计算结果。

## 3. 请求完成与资源结束

请求结束不一定意味着它创建的资源结束。

| 命令 | 请求何时完成 | 完成后是否留下活动资源 |
| --- | --- | --- |
| drive click / input / long-press / scroll | 输入达到 SDK 承诺的完成边界 | 不创建持续资源；业务影响仍可能继续 |
| drive wait | 条件满足或等待超时 | 不创建持续资源 |
| override method / field / code / apply | 安装完成，清理闭包保存并登记成功 | 留下覆盖资源 |
| inspect 的 watch 类命令 | 观测安装并登记成功 | 留下 watcher |
| override remove | 对应清理调用完成或失败 | 成功时结束覆盖；失败时保留诊断状态 |

inspect 的具体 CLI 命令形态另行定义。

### 一次性等待

```bash
aeu drive wait --target R.id.search_results --state visible --timeout-ms 5000
```

CLI 在前台等待最终响应；Host 路由请求，App 运行时执行 UI 等待。条件满足或超时后，结果沿原路径返回，CLI 输出并退出。CLI 可以通过异步 I/O 等待，不阻塞 App 主线程；轮询及线程调度遵循 SDK 契约。

需要区分三个时间边界：

- wait 超时：条件最多等待多久，由 SDK 等待选项控制。
- 通信超时：等待运行时响应的期限，应为操作完成和返回留出余量。
- Agent 执行工具的等待窗口：工具可能先返回进程 ID，之后继续读取结果，不一定终止 CLI。

客户端停止等待或通信超时，不证明底层操作已取消。前台 CLI 等待也不意味着 Host 必须阻塞所有其他客户端；具体并发与取消协议另行定义。

### 持续覆盖

安装请求完成后，CLI 返回 overrideId 并退出，运行时保留覆盖与清理函数。

```text
override remove ov-1
  → Host 找到会话和运行时资源 r-7
  → 运行时调用保存的 remove()
  → Host 接收并登记清理结果
  → CLI 输出结果并退出
```

并发 remove 应共用首次清理操作。当前 SDK override 闭包不会重试失败步骤，Host 不能再次调用空操作后将先前失败改报成功。具体语义见 [override CLI](override.md)。

## 4. 设备、App 与会话选择

设备选择采用 adb 风格：

```bash
aeu devices
ieu devices
aeu -s <serial> connect --app com.example.demo
ieu -s <udid> connect --app com.example.demo
```

- 指定 -s 时只选择该设备，不可用时报错，不回退。
- 未指定且只有一个可用设备时自动选择。
- 未指定且有多个可用设备时报错并列出设备，要求明确选择。
- 无可用设备时报错，提供设备发现结果。

可用设备指能建立控制连接的设备，不要求目标 App 已经连接。devices 可同时列出发现但不可用的设备及原因。

设备唯一不代表 App 唯一。connect 显式指定 App；连接完成应意味着 SDK 运行时就绪，可以接收命令。App 启动、注入及平台后端准备方式分别定义。

业务命令先选择设备，再选择设备内会话：

- 一个活动 App 会话：默认使用。
- 多个活动 App 会话：要求 --session 指定。
- 无活动 App 会话：提示先 connect，不猜测前台 App。

每条请求解析并绑定一次设备、会话及运行时身份，执行过程中不因设备列表变化自动切换。结果应携带实际目标身份；公共输出结构另行确定。不同终端不通过“最近一次连接”隐式改变其他命令的目标。

## 5. 为什么不能每条命令都重新连接

独立的一次性操作可能允许连接、执行、断开，但这不足以承载完整运行时能力：

- watcher 的采集回调与累计缓存需要跨命令保留。
- override 的原方法信息和清理闭包需要留给后续 remove。
- 原生对象引用、调试器断点和在途事件具有自己的生命周期。
- 反复卸载与重建运行时会破坏这些状态，不能视为透明连接复用。

把资源 ID 写到磁盘只能保存标识与元数据，无法让 JS 闭包、hook、原生对象和通信连接继续运行。资源登记的持久化可用于诊断和恢复核对，但不能替代存活的运行时，也不表示任意资源能够跨进程重启恢复。

## 6. 退出、断连与失效

| 事件 | 语义 |
| --- | --- |
| CLI 正常退出 | 结束本次客户端请求，不自动结束会话或持续资源 |
| Ctrl+C / 客户端断开 | 客户端停止等待；请求可能已经执行，取消是否生效必须明确报告 |
| 显式 disconnect | 进入会话关闭流程，尝试清理资源并关闭连接；报告清理与关闭失败 |
| App 退出或 SDK 运行时卸载 | 原资源失效；新进程或新运行时不能复用旧资源身份 |
| Host 服务异常退出 | 需重新确认连接与资源状态，不能仅凭磁盘记录宣称恢复成功 |

disconnect 的清理顺序需要遵守平台约束，例如 iOS 同方法多次覆盖必须逆序移除，code 资源应在 debugger detach 前移除。资源清理不等于业务状态回滚，field setter 的副作用、已经执行的 code 修改或已经发出的请求不会因此自动撤销。

通信丢失时，Host 可能无法判断操作是否完成。不能自动重放完成状态未知的输入或覆盖安装请求；需要请求身份、资源记录与状态查询支持核对，具体协议待设计。

会话身份必须区分不同进程与不同 SDK 运行时实例，不能只依赖可能被复用的 PID。断连后的底层资源是否仍然存活、如何释放，取决于平台后端；未确认时应报告未知或失效，而不是宣称已恢复原状态。

## 7. 后续实现需要收敛的内容

1. 本地服务启动、版本兼容、IPC 和多客户端请求调度。
2. 设备、会话、运行时与资源的身份协议。
3. 安装与登记的失败处理、请求去重及响应丢失后的核对方式。
4. 超时、取消、disconnect 清理和服务异常退出策略。
5. 脚本模块的保活、依赖加载、资源清理后的卸载，以及证据持久化。

这些机制属于 CLI 控制与运行时管理层，不要求业务 SDK 的每个 API 都新增 scope、registry 或资源 ID。
