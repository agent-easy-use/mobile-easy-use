# 测试设计与 Agent 修改约定

本文是本项目测试建设的设计约定。Agent 新增、迁移或修改测试时应遵循本文；用户明确要求的调整优先。本文描述目标模式，不表示现有测试已全部迁移，也不表示设备能力已全部验证。

## 1. 目标

验证 SDK 变更后，通过实际执行链路调用 API，仍能得到正确的 App 行为、准确的观测结果，并正确清理资源。

业务 API 以 Android Emulator / iOS Simulator 上的 ApiDemo E2E 为主要验收依据。模拟器测试运行真实 App、SDK 和原生运行时，不 mock Frida、LLDB 或被测原生能力。模拟器通过不等于真机兼容性已验证；真机只补充平台专属链路和关键冒烟，不机械复制全部用例。

测试类型由验证范围决定，与是否使用 Node 的测试运行器无关：

- 单元测试：独立逻辑的输入输出或状态行为，不必使用 mock。
- 集成测试：真实组件间的配合，如 LLDB worker 调试 macOS 原生程序。
- E2E：通过实际 SDK 执行链路操作模拟器 App，并验证最终效果。

## 2. 目录与职责

沿用现有 ApiDemo，避免再建平行测试体系：

```text
fixtures/android/ApiDemo/tests/   Android App 内的 SDK 测试脚本
fixtures/ios/ApiDemo/tests/       iOS App 内的 SDK 测试脚本
test/e2e/                        Host E2E 入口和必要的执行编排（按需建设）
test/*.test.js                   现有测试，逐步评估，不要求整体迁移
```

- 双端测试脚本分开，靠近各自依赖的原生场景，核心场景名称和验收标准对齐。
- `ApiDemo/tests/` 必须按能力划分子目录，子目录名与对应平台 `sdk/{platform}/` 的实际子目录名保持一致，不使用 API 别名替代。例如当前覆盖能力的目录名是 `overrides`，不是 `override`。
- 测试文件放入对应子目录，例如 `tests/drive/input.js`、`tests/inspect/code.js`、`tests/overrides/method.js`；新增或迁移用例不得继续平铺在 `tests/` 根目录。
- 能力专属辅助脚本按需放入对应能力目录的 `helpers/`，测试发现必须排除辅助文件。执行入口应支持发现能力子目录中的测试文件。
- 允许少量双端重复；只有出现稳定、真正一致的逻辑时才提取公共代码，不预建跨平台适配框架。
- 不为了此次设计批量移动旧测试或新建 `test/unit/`。迁移应伴随具体能力的实现和验证。

## 3. Host 运行壳保持薄

Host 入口运行在 Mac，App 内测试脚本运行在模拟器的 App 进程中。

```text
Host 选择平台、设备和测试文件
  → 复用实际连接与脚本加载链路
  → 在 App 内调用测试脚本 run()
  → 接收报告
  → 汇总结果、保存失败信息、设置退出码
```

- iOS E2E 使用 `test/e2e/config.json` 中的 UDID，支持 `--device` 覆盖；未启动时自动启动并等待系统就绪，结束后保留模拟器。
- Android E2E 使用 `test/e2e/config.json` 中的 AVD 和端口；未启动时自动启动并等待开机完成，结束后保留模拟器。不自动下载镜像或创建 AVD；显式 `--device` 可覆盖设备选择。
- 环境准备复用已有安装和启动能力，双端从 `test/e2e/config.json` 的 `artifact` 路径安装预构建 APK / 模拟器 `.app`，不在 E2E 中编译原生集成库或 ApiDemo；测试执行复用产品已有的连接、SDK 加载、Controller 和脚本执行能力。
- 一个命令可以串联准备和执行，但不得在测试目录重新实现另一套产品运行链路。
- Host 只负责选择、编排、超时、崩溃/断连处理、报告和最终连接清理，不理解具体 API 的业务预期，不复制 App 内断言。
- 双端共享执行流程，保留必要的平台差异；不预建插件机制、通用执行器或复杂配置系统。
- 优先按目录发现脚本，不额外维护重复的用例注册表。
- 原生安装产物由调用方预先构建；报告记录产物路径并标明未重建，不将其描述为当前原生源码已通过。SDK JS、presets 和测试脚本仍使用当前源码构建。
- 不将仅验证测试模块注册或加载的 Host mock 测试，标记为 ApiDemo E2E 已通过。

## 4. App 内测试脚本契约

沿用已有 `Test.create()`、`run()` 和结构化报告，不创建第二套断言或报告协议。

```javascript
const { describe, test, beforeEach, afterEach, expect, run } = Test.create();
export { run };
```

- 每个文件创建独立测试集合。加载时只注册用例，不连接设备、不操作 App。
- 测试通过真实 SDK 执行被测操作，使用项目的 test/expect 断言。
- beforeEach 建立已知状态；afterEach 清理本用例创建的 watcher、override 和业务状态。
- 断言失败后仍需执行清理。原始错误和清理错误均应保留，不能互相覆盖。
- 测试不依赖其他用例先执行，也不依赖上一次运行遗留的状态。
- 原生类型和配置按平台编写，不用大量平台条件分支强行共用脚本。

### 测试代码可读性

以不熟悉实现的开发者能否顺序读懂为标准：读完一个 `test`，应能直接看出准备了什么、调用了什么、预期什么。代码行数少不是目标。

- 被测 API 调用和核心结果断言放在 `test` 正文中。避免用 `clickAndExpect(target, 2)` 一类函数把操作、等待和验证全部藏起来，也避免让数字参数的含义依赖阅读实现才能确定。
- 辅助函数用于场景准备、状态读取、坐标计算和重复等待。名字表达具体动作或结果，如 `openClickScene`、`returnHome`、`waitForClickCount`；不使用含义模糊的 `home`。同名函数在双端应有一致的完成语义。
- 按执行顺序拆开原生调用、类型转换、数据解析和字段读取。避免多层 `await`、属性访问和断言嵌套在一行；普通多行 `try/finally` 优于压缩写法。
- 断言描述与实际比较一致：累计值写累计值，增量写增量。“状态未改变”应比较操作前后的状态，不在辅助逻辑中暗含初始值为零。
- 测试名只描述已经验证的行为。例如接受数组路径不等于验证了父级范围隔离；后者需要范围外的干扰目标和可区分的结果。
- 原生常量使用可读名称或注释说明。按已确认的 Frida 类型编写代码，不添加没有依据的多种数据格式兼容分支。
- 保留适量重复，让各用例能独立阅读。相同操作和断言下的无效参数可以表驱动；行为不同的场景不要为了合并而加入分支或搭建通用测试框架。
- `beforeEach` 只建立必要前置状态，检查关键就绪条件；不要为每个准备步骤堆断言。必要等待失败必须及时终止并说明原因，不能忽略结果后继续执行。

### 准备流程与被测能力分离

场景准备不能依赖正在验证的操作。例如 `drive.click` 用例使用原生入口或原生按钮事件完成导航，在测试正文中通过 `drive.click` 执行被测点击。这样点击能力回归时，失败落在实际验证步骤，而不是准备流程。

原生准备代码需注释说明这个原因，以及它直接触发业务处理而非注入真实输入。此规则针对被测操作，不禁止使用其他辅助 API，例如 click 用例中的 `drive.wait`。不为此预建复杂的原生场景框架，优先复用已有入口。

## 5. ApiDemo 提供独立、可控的验证依据

原生场景按需提供简单的重置入口、确定输入的触发入口、完成标记、结果读取入口，以及稳定 UI 标识或源码标记。

辅助入口用于准备和验证，不得替代被测能力或复制 SDK 实现。例如点击测试可以直接重置、读取原生计数器，但点击必须经过 drive API。

| 能力 | 必须关注的实际结果 |
| --- | --- |
| drive / target | 操作正确目标，App 状态按预期改变，触发次数正确 |
| inspect | 真实现场采集值准确，条件过滤正确，不同 watcher 相互独立 |
| override | 原生调用方实际得到覆盖效果，remove 后恢复正常行为 |
| 生命周期 | stop/卸载后不再产生对应效果，其他注册及后续操作仍正常 |

API 返回 `ok`、方法被调用、命令被发送，均不能单独证明原生能力生效。earlyReturn 必须验证原生调用方实际收到的返回值。

每个用例应明确：保护什么行为、通过什么结果判断、哪种真实错误会使它失败、在哪个运行入口执行。不要仅根据测试名称或数量宣称覆盖。

## 6. 等待、隔离和故障恢复

- 第一版在同一模拟器/App 内顺序执行，不并行操作共享业务状态。
- 一次运行复用模拟器；正常情况下复用 App 和连接，不为每条用例重启设备。
- 等待使用明确完成条件和截止时间，不用固定 sleep 猜测完成。
- 断言“没有记录”之前，先确认相关原生工作完成，避免过早检查造成假通过。
- Host 设置独立超时，App 内脚本失联后也能结束测试并报告失败。
- 发生崩溃、超时或清理失败时，不假定环境仍干净；明确恢复到已知状态后再继续，否则停止并报告剩余用例未执行。
- 默认不自动重试失败用例以掩盖偶发问题。

## 7. Host 生命周期用例是必要例外

脚本卸载、App 重启、断连和重连不能全部依赖原脚本完成断言。这类少量用例允许 Host 编排，并复用同一连接工具。例如：

```text
加载脚本 A → 安装覆盖并验证生效
  → 卸载脚本 A
  → 加载验证脚本 B → 检查原生行为已恢复
```

不要为统一形式给所有 App 内用例增加复杂生命周期协议，也不要只检查 Host 的 closed 标记就认定原生资源清理成功。

## 8. 报告与执行结果

复用 App 内 Test 报告，Host 外层补充平台、设备标识、系统版本、产物信息、耗时和基础设施错误。失败证据按需保存：UI 截图、App 日志、脚本错误、LLDB 诊断等；收集失败不能覆盖原始错误。

- 指定用例全部执行且通过，退出码才为 0。
- 断言失败、环境准备失败、超时、崩溃、断连或指定执行未完成，返回非零退出码。
- 明确区分通过、失败、未执行；环境不可用不能静默跳过后宣称全部验证完成。
- 调查复现脚本与正常回归用例区分。打印异常却以 0 退出，不构成有效失败检测。
- 报告实际验证范围；macOS 宿主测试不代表 iOS 模拟器通过，模拟器通过不代表真机通过。

## 9. 无设备测试的保留标准

不为每个 API 机械补一套 mock 测试。优先保留：

- test/expect 自身的正确性，尤其错误预期确实失败。
- 测试筛选、统计、错误汇总以及 Host 的失败退出码。
- 独立的结果处理逻辑。
- 少量难以在真实环境中稳定制造的通信失败、重试和请求并发行为。

macOS 原生程序上的真实 Frida/LLDB 测试可以保留，用于快速隔离底层问题，但不替代 ApiDemo E2E。

对紧贴实现的断言进行价值评估：仅断言调用了某个内部方法，不能承担对应原生行为的保障。已有稳定 E2E 覆盖后，不重复维护同一行为的低价值 mock 用例；删除前确认它没有额外保护独立的故障或时序场景。

## 10. Agent 落地要求

1. 先检查现有 ApiDemo 场景、脚本和运行工具，优先复用，不重复造轮子。
2. 先跑通双端最小实际场景，再按能力逐步迁移新 API 用例；不先重构整个测试目录。
3. 建设运行入口时，主动验证一次断言失败和一次超时，确保报告、退出码和清理确实有效。
4. 不通过放宽断言、吞掉异常、静默 skip 或改成检查内部调用来使测试变绿。
5. 区分“新增了用例”“实际运行通过”“未在该环境验证”；只报告有证据的结论。
6. 新增文件、测试入口和运行约定应与本文一致；实际设计发生经用户确认的变化时同步更新本文。
